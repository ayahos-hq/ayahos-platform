## PostgreSQL migrations and Spine retention

### Gap found and fixed

`PostgresSpineStore.apply_retention()` (bounded archive/purge pass, `SpineRetentionPolicy`: archive
terminal histories after 7 days, purge archived payloads 30 days after archival, batch 1000) had no
caller. No CLI, endpoint, or scheduled job ran it, so retention could not have run on any
deployment. The Ruby `archive_incidents` job reads incidents through the API into a JSON file; it
does not run a database retention pass.

This change adds `python -m dual_lineage.db retention`. It runs one pass with the Python-owned
policy and prints JSON counts (`archived_requests`, `purged_archived_events`) together with the
policy windows. The current `render.yaml` intentionally does not schedule this background job;
Render is reserved for the lightweight API/control gateway. A Node 1/cloud scheduler must invoke it
with the private `DATABASE_URL`, and the external deployment and successful live invocation remain
unverified.

| --- | --- | --- |

Two consecutive runs on the same database also pass |
